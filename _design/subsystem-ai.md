# SUBSYSTEM: ai

## Summary
Granny is a 7-state FSM (Patrol → Investigate → Chase → Search → Attack → Stunned → Return) driven by two perception channels: a HEARING system that consumes discrete noise events (position + loudness radius) and a SIGHT system (vision cone FOV+range gated by a per-frame line-of-sight raycast) that fills a 0–100 awareness meter. She navigates a 0.5 m grid over the house using A* with an 8-direction neighbor model; the grid is dynamic — when the player pushes furniture or barricades a door, the affected cells flip to blocked and paths re-plan. At a barricaded door she chooses to open (fast), shove the blocking furniture aside (medium), or break the door (slow) based on door type and how long she's been blocked. She runs as a kinematic cannon-es capsule whose velocity is driven by the path, with a catch radius that triggers a lunge-attack. Difficulty scales speeds, FOV, hearing radius, awareness fill rate, and search persistence. Anti-cheese measures (predictive intercept, shortcut knowledge, vault/shove of light furniture, a "frustration" timer that escalates door-breaking, and a brief teleport-reposition only when fully lost) stop the player from looping her around a table while keeping her fair (telegraphed by audio, always physically present, never sees through walls).

## Key Decisions
- FSM with 7 explicit states rather than behavior tree — easier to make transitions and timers deterministic and debuggable, which the client demands. Each state owns its movement speed, animation, and audio cue.
- Perception is split into two independent channels (hearing = event-driven, sight = polled per frame) that both feed ONE shared 'lastKnownPlayerPos' + 'awareness' blackboard. State transitions read the blackboard, not the raw senses — keeps senses decoupled from logic.
- Navigation uses a UNIFORM GRID (cell 0.5 m) baked from the level + rebuilt incrementally when physics moves furniture, NOT a static navmesh. A navmesh cannot cheaply represent the player pushing a couch into a doorway; a grid with per-cell dynamic-blocked flags can flip cells in O(1) when a body crosses them.
- Granny's body is a KINEMATIC cannon-es capsule (we set its velocity from the path), NOT a dynamic body. A dynamic body would jitter against walls and could be shoved by the player — she must be immovable and tunnel-proof. She still generates collision events so she can physically open/push doors and furniture via applied impulses.
- Awareness meter (0–100) decouples 'I glimpsed the player' from 'I am now chasing'. Prevents instant snap-to-chase on a single frame of LOS (unfair) and prevents flickering between Patrol/Chase.
- Line-of-sight is a SINGLE raycast eye→player-chest per frame (plus optional 2 offset rays at higher difficulty), against a dedicated low-poly collision world, NOT against render meshes — keeps it cheap and correct.
- Anti-cheese 'predictive intercept': when chasing with LOS, Granny paths to a point ahead of the player's velocity, not to the player's current cell, so she cuts corners instead of tailing forever around a loop.

## Data Model
Granny owns a blackboard object: state (enum), stateTimer (s, time in current state), prevState; awareness (0–100 float); lastKnownPlayerPos (Vec3 | null) and lastKnownPlayerVel (Vec3); investigateTarget (Vec3) with uncertaintyRadius (m); searchPointsRemaining (Vec3[]); hasLOS (bool, this frame); distToPlayer (m); body (cannon kinematic capsule, radius 0.30 m, height 1.45 m hunched); currentPath (Vec3[] waypoints) + pathIndex; pathAge (s, for re-plan throttle); blockedTimer (s, time stuck against an obstacle); targetDoor / targetFurniture handles for interaction; frustration (0–100, anti-cheese escalation); speed (m/s, derived from state+difficulty); difficulty params (struct, see tunables). Shared with NoiseSystem via a noiseQueue (array of {pos:Vec3, loudness:number, time}). The nav grid: 2D array of cells {walkable:bool, staticBlocked:bool, dynamicBlocked:bool, cost:float}, cellSize 0.5 m, plus a doorNodes list linking grid regions through door bodies.

## Public Interface
- new GrannyAI(world, navGrid, player, audio, level) — constructs the kinematic body, places her at a spawn waypoint, sets state=PATROL.
- GrannyAI.update(dt) — main tick: (1) drain noiseQueue via hearNoise, (2) updateSight (cone test + LOS raycast + awareness), (3) FSM transition logic, (4) movement/path follow, (5) door/furniture interaction, (6) drive audio. Call once per frame with real dt clamped to <= 0.05 s.
- GrannyAI.hearNoise(pos, loudness) — called by NoiseSystem (or pulled from queue) when player emits sound; returns true if the noise was within effective hearing radius and was acted on. loudness 0..1.
- GrannyAI.onSeenPlayer(visibleFraction, dist) — internal, called by updateSight; raises awareness by fillRate*visibleFraction*dt scaled by distance falloff.
- GrannyAI.requestPath(fromCell, toCell) -> Vec3[] | null — A* over the dynamic grid; null if unreachable (triggers door-break logic if a door is the blocker).
- NavGrid.markDynamicBlocked(aabb, blocked) — called by physics step when a furniture/door body's AABB moves; flips overlapped cells, bumps a grid version counter so Granny knows to re-plan.
- NavGrid.worldToCell(vec3) / cellToWorld(cell) — coordinate mapping.
- GrannyAI.setDifficulty(level) — 'easy'|'normal'|'hard'|'nightmare', swaps the difficulty param struct.
- GrannyAI.getStateForAudio() / getStateForUI() — exposes current state so the audio module plays the right footstep/breath/mutter loop and the UI can show a (subtle) heartbeat intensity.

## Tunables
- cellSize = 0.50 m — nav grid resolution (door width ~0.9 m = ~2 cells, so doors are never fully blocked by rounding)
- body.radius = 0.30 m, body.height = 1.45 m (hunched), body.mass = kinematic (infinite)
- grannyEyeHeight = 1.30 m — raycast origin for LOS
- visionFOV = 100 deg total (±50 deg from facing) [normal]
- visionRange = 12 m [normal] — hard cutoff for the cone
- visionRangeDark = 6 m — range when player is in an unlit room and flashlight off
- losRaysPerFrame = 1 [easy/normal], 3 [hard+] (chest + 2 shoulder offsets)
- awarenessMax = 100
- awarenessFillRate = 70 /s at 0 m falling to 25 /s at visionRange (linear distance falloff) [normal]
- spottedThreshold = 100 → enter Chase; partialThreshold = 40 → enter Investigate toward sighting
- awarenessDecayRate = 18 /s when no LOS (starts after 0.5 s grace) [normal]
- hearing baseRadius = 14 m [normal] — max distance she can register the LOUDEST noise
- noise loudness: sprint footstep = 1.0 (radius 14 m), walk = 0.5 (7 m), crouch-walk = 0.12 (1.7 m), idle/still = 0, object drop = 0.85 (12 m), door slam = 1.0 (14 m), barricade scrape = 0.7 (10 m). effectiveRadius = baseRadius * loudness
- investigate uncertaintyRadius = clamp(2 m + (1 - loudness)*4 m, 2 m, 6 m) — quieter noises = vaguer target
- speed.patrol = 1.1 m/s, speed.investigate = 1.8 m/s, speed.search = 1.5 m/s, speed.chase = 3.0 m/s [normal] (player walk 2.6, sprint 4.6, crouch 1.2)
- catchRadius = 1.1 m — within this during Chase, transition to Attack
- attackLungeSpeed = 4.5 m/s for 0.35 s; attack resolves (player caught) if still within 1.3 m at lunge end
- stunDuration = 4.0 s (hit by thrown/swung object); reduces to 2.5 s on each subsequent stun (diminishing)
- investigateTimeout = 8 s (no find → Search), searchDuration = 18 s total / 5 search points, searchPointTimeout = 3.5 s each
- returnToPatrolDelay = after Search ends with no contact
- rePlanInterval = 0.4 s (throttle A*), forced re-plan on grid version change
- blockedTimer thresholds: 0.8 s → try open door, 2.0 s → shove furniture, 4.0 s → break door
- doorOpenTime = 0.5 s, furnitureShoveImpulse = 35 N·s, doorBreakTime = 3.0 s (wood) / never (locked metal — must reroute)
- frustration: +12/s while blocked or while player kites in a loop, -8/s otherwise; at >=80 unlocks break-door and a one-time reposition
- repositionCooldown = 25 s — only fires when awareness>0 but no LOS for 6 s AND path length to lastKnownPos > 25 m
- difficulty multipliers (easy→nightmare): chaseSpeed x0.85→x1.25, FOV 80→120 deg, hearingRadius x0.7→x1.3, awarenessFill x0.7→x1.4, searchDuration x0.7→x1.5

## Algorithms
- PER-FRAME UPDATE ORDER (must be this order to avoid 1-frame lag bugs): 1) clamp dt; 2) drain noiseQueue → hearNoise() updates blackboard lastKnownPlayerPos/investigateTarget; 3) updateSight() — cone test then LOS raycast then awareness integrate/decay; 4) FSM evaluateTransitions() reading blackboard; 5) if grid version changed since last plan OR pathAge>rePlanInterval, requestPath(); 6) followPath() sets kinematic body.velocity toward currentPath[pathIndex]; 7) door/furniture interaction check; 8) physics world.step() happens in the main loop AFTER this; 9) updateAudio(state).
- HEARING: for each noise event, effectiveRadius = baseRadius*hearingMult*loudness. If distance(granny, noise.pos) <= effectiveRadius, it's heard. Set lastKnownPlayerPos = noise.pos jittered by a random offset within uncertaintyRadius (so she walks TO A SPOT NEAR the sound, not exactly on the player — feels organic and prevents wallhack precision). If currently PATROL/RETURN → go INVESTIGATE. If already INVESTIGATE/SEARCH and new noise is louder/closer → retarget. Noises do NOT directly trigger Chase (only sight does); but a loud noise within 5 m while already Investigating raises awareness by 30 to bias toward catching.
- SIGHT: (a) vector eye→playerChest; if angle to granny.facing > FOV/2 → not in cone, skip. (b) if dist > effectiveVisionRange (use Dark range if player unlit+flashlight off) → skip. (c) cast losRaysPerFrame rays from eye to player sample points against the COLLISION world only; visibleFraction = (#unobstructed rays)/(total). (d) if visibleFraction>0: awareness += fillRate(dist)*visibleFraction*dt; set lastKnownPlayerPos=playerPos, lastKnownPlayerVel=playerVel, hasLOS=true, reset losGraceTimer. (e) else hasLOS=false; after 0.5 s grace, awareness -= decayRate*dt. Clamp 0..100.
- AWARENESS→STATE: awareness>=spottedThreshold → CHASE. awareness in [partialThreshold,spotted) and not chasing → INVESTIGATE toward lastKnownPlayerPos. In CHASE, if awareness drops to 0 (lost LOS long enough) → SEARCH around lastKnownPlayerPos.
- A* PATHFIND: nodes = walkable cells (staticBlocked=false AND dynamicBlocked=false). 8-neighbor, diagonal cost 1.414, cardinal 1.0, plus per-cell cost penalty near walls (+0.3) so she hugs centers not corners. Heuristic = octile distance. Door cells are walkable ONLY if door is open OR breakable-and-she-intends-to-break. If openSet empties with no path → unreachable → invoke door/break or reposition logic. Smooth the path with string-pulling (line-of-sight cell raycast between waypoints) to remove zigzag.
- DYNAMIC OBSTACLES: each physics step, for every furniture/door body whose AABB moved > 0.1 m, call markDynamicBlocked: clear its old cells, set its new cells. Bump grid.version. On next Granny tick she sees version change and re-plans. This is how a pushed couch in a doorway actually blocks her.
- BARRICADED DOOR DECISION: when followPath stalls (blockedTimer rising) at a door node: if door simply closed (not blocked) and openable → play reach animation, apply hinge impulse, wait doorOpenTime (0.5 s). If furniture is wedging it and item mass < shoveMassLimit (40 kg) and blockedTimer>2.0 s → apply furnitureShoveImpulse to clear it. If door is breakable wood and blockedTimer>4.0 s (or frustration>=80) → play break over doorBreakTime (3.0 s, loud audio telegraph), then set door cells walkable. If door is locked metal → mark unreachable-via-here, re-plan an alternate route; if no alternate, fall back to Search/reposition.
- CATCH/ATTACK: in CHASE, if distToPlayer<=catchRadius → ATTACK: lunge (velocity toward player at attackLungeSpeed for 0.35 s). At lunge end, if distToPlayer<=1.3 m → player caught (game over / jail). Else missed → back to CHASE (with a 0.4 s recovery where speed=0, the player's escape window). This recovery is the fair counterplay.
- ANTI-CHEESE PREDICTIVE INTERCEPT: in CHASE with hasLOS, target = playerPos + playerVel * leadTime where leadTime = clamp(distToPlayer / chaseSpeed, 0.2, 1.0) s. Path to the predicted cell. Combined with corner-cutting string-pulled paths, she cuts across the table loop instead of chasing the player's tail. Also: detect loop-kiting (player stays within a 5 m radius region while Granny's path keeps circling for >4 s) → frustration spikes, she vaults/shoves the table (if mass<shoveMassLimit) or takes the geometrically shorter arc.
- FRUSTRATION/REPOSITION: frustration rises while blocked or loop-kited. At >=80 it unlocks door-breaking and, if awareness>0 but no LOS for 6 s and path-to-lastKnown>25 m, a ONE-TIME reposition: she moves (off-screen, never in player's view cone — verify with a reverse LOS check) to a waypoint nearer lastKnownPlayerPos, then resumes Search. Cooldown 25 s. This is the 'she's always somewhere near' tension without teleport-cheating in view.

## Pitfalls
- MISTAKE: making Granny a dynamic rigid body — she jitters against walls, gets shoved by the player, and tunnels at speed. FIX: kinematic body, set body.velocity each frame, use cannon-es CCD/swept checks; never apply gravity to her; she pushes the world via collision events + manual impulses on furniture/doors, the world never pushes her.
- MISTAKE: instant Chase on a single frame of LOS — feels like a wallhack/aimbot, deeply unfair. FIX: awareness meter must FILL over time (spottedThreshold=100 at fillRate~70/s ≈ 1.4 s of clear sight at point blank, longer at range). A fleeting glimpse only nudges it.
- MISTAKE: LOS raycast against the render meshes (with cobwebs, decals, high-poly Granny) — slow and gives false blocks. FIX: cast only against a dedicated simplified collision layer; ignore the player's own body, items, and Granny herself in the raycast filter.
- MISTAKE: she sees through walls because the cone test passes and nobody did the raycast, or the ray hits the player but you forgot the wall was on a non-collidable layer. FIX: cone test is necessary-not-sufficient; ALWAYS require the LOS ray to reach the player unobstructed. Unit-test with a wall between them.
- MISTAKE: re-running A* every frame — frame drops in a big house. FIX: throttle to rePlanInterval (0.4 s) and additionally re-plan immediately only when grid.version changes; reuse current path otherwise; cap A* expanded nodes (e.g. 4000) and bail to partial path.
- MISTAKE: pushed furniture in a doorway does NOT block her because the grid was baked once at load. FIX: incremental markDynamicBlocked on AABB movement + grid version bump + forced re-plan. Test by shoving a couch into a hall and confirming she reroutes.
- MISTAKE: items/furniture cells flip blocked but the door's 2-cell opening rounds to 1 blocked cell, so she thinks an open door is shut. FIX: cellSize 0.5 m so a 0.9 m door spans ~2 cells; mark a cell blocked only if obstacle AABB covers > 60% of it.
- MISTAKE: player loops her around a table forever (the #1 complaint). FIX: predictive intercept + corner-cutting string-pulled paths + loop-kite detection that makes her cut the chord or shove the table. She should close the loop within ~2 turns.
- MISTAKE: awareness flickers between thresholds causing rapid Investigate↔Chase state thrash. FIX: hysteresis — enter Chase at 100, only leave Chase when awareness hits 0 (not 99); 0.5 s LOS-loss grace before decay starts.
- MISTAKE: she breaks/teleports unfairly and the player never feels they had a chance. FIX: every aggressive action is AUDIO-TELEGRAPHED (door-break = 3 s of loud cracking, footsteps speed up audibly in Chase, a mutter/groan on state change) and the reposition only happens off-camera with a reverse-LOS check and a 25 s cooldown.
- MISTAKE: kinematic body at chaseSpeed tunnels through a thin door/wall between physics steps. FIX: clamp dt<=0.05 s, enable swept/CCD for her body, and cap per-step displacement to < body.radius (0.30 m); if a step would exceed it, subdivide.
- MISTAKE: noise event sets lastKnownPos exactly on the player, giving her pixel-perfect knowledge from a sound — feels like cheating. FIX: jitter the investigate target within uncertaintyRadius (2–6 m, larger for quieter sounds); she searches the AREA, not the exact spot.

## Risks
- Dynamic grid rebuild cost: if many bodies move at once (player knocks over a shelf), markDynamicBlocked + re-plan could spike a frame. Mitigate by batching AABB updates per physics step and only re-planning if Granny's CURRENT path intersects a changed cell.
- cannon-es kinematic-vs-dynamic interaction for door/furniture shoving is finicky — applied impulses may over/under-shoot. Needs tuning of furnitureShoveImpulse and possibly a constraint-based push instead of a one-shot impulse.
- Tuning fairness is empirical: spottedThreshold timing, chaseSpeed vs sprint, and catch recovery window all need playtesting; the listed numbers are starting values, not final. Risk of shipping her as either trivial or impossible without iteration.
- Path string-pulling LOS checks across the grid add cost; if the collision world is complex it may misreport. Validate the cell-raycast against the same collision layer used for sight.
- Reposition logic is the highest-risk anti-cheese feature — if the off-camera/reverse-LOS check is wrong she'll appear to teleport in front of the player and the client will (rightly) call it broken. Gate it hard and default it OFF on easy.
- FSM/perception/audio coupling: if audio cues lag the state by a frame or two the telegraph breaks and she feels unfair. Drive audio from the same blackboard within the same update, not from a delayed event.

## CRITIQUE (worksProbability=0.28)
Verdict: Architecturally sound and unusually well-thought-out for a first pass — the FSM/blackboard split, awareness-meter decoupling, and audio-telegraphed aggression are correct instincts. But it WILL NOT work as written on an integrated build, for three structural reasons the design hand-waves: (1) the update-order contradicts itself — sight reads the player position and Granny's facing BEFORE physics steps, but Granny's facing/position only exist after the kinematic integration, producing a guaranteed 1-frame perception lag and a chicken-and-egg on 'who moved first'; (2) the dynamic-grid coordinate story is fatally underspecified — there is no stated origin, bounds, multi-floor handling, or per-frame AABB-to-cell cost budget, and cannon-es does NOT give you a free per-body 'AABB moved >0.1m' signal, so the whole 'pushed couch blocks her' centerpiece has no actual data source; (3) cannon-es kinematic bodies do NOT have working CCD/swept collision (the pitfall 'use cannon-es CCD' is citing a feature that effectively does not exist in cannon-es), so the anti-tunneling fix is fiction and the real fix (manual sub-stepped raycasts) is not designed. Several numbers are also internally inconsistent (catchRadius vs attack resolve distance, chaseSpeed barely faster than sprint, awareness decay lets the player win every chase by breaking LOS for 5.6s). This is a strong DESIGN DOC that is roughly 40% of an implementable SPEC. It needs the integration contract nailed down or a careless implementer ships a Granny that lags a frame, sees through pushed furniture, occasionally tunnels through doors at chase speed, and loses every chase.

### Fatal Flaws
- UPDATE ORDER IS SELF-CONTRADICTORY AND CAUSES GUARANTEED 1-FRAME PERCEPTION/MOVEMENT LAG. The design says: drain noise -> updateSight -> FSM -> followPath sets body.velocity -> THEN world.step() in main loop. But updateSight needs Granny's CURRENT facing and position, and followPath needs the path planned from her CURRENT cell. After world.step() integrates her kinematic velocity, her position changes — so on frame N she perceives/plans from frame N-1's pose. Worse: the player's body is ALSO stepped in the same world.step(). So LOS on frame N is cast against the player's frame N-1 position AND walls in frame N-1 state. At chase speed (3 m/s) and 16.6ms frames this is ~5cm of stale data per frame, which is tolerable for position but the real bug is corner-peek: the player rounds a corner, Granny's LOS ray on the frame the wall clears is computed against PRE-step transforms, so she gets one extra frame of false negative AND one frame later a false positive — perception feels 'sticky' and unfair in both directions.
- THE DYNAMIC-GRID CENTERPIECE HAS NO DATA SOURCE. The design asserts 'each physics step, for every furniture/door body whose AABB moved > 0.1 m, call markDynamicBlocked.' cannon-es does NOT emit a 'body moved' event and does NOT maintain a cheap per-body world AABB delta you can poll for free. You must, every step, iterate ALL movable bodies, read body.aabb (which is only updated if you call body.computeAABB() or aabbNeedsUpdate is set), diff against a stored previous AABB, and on change rasterize the AABB into grid cells. With ~30-60 movable items this is fine, but it is NOT designed, has no cost budget, and the naive implementation recomputes AABBs the broadphase already computed, doubling cost. Without this nailed down, the implementer either (a) skips it and pushed furniture never blocks Granny (client's #1 furious complaint), or (b) does it per-frame against render meshes and tanks the frame.
- CANNON-ES HAS NO WORKING CCD FOR THE ANTI-TUNNELING FIX. Pitfall says 'use cannon-es CCD/swept checks' and 'enable swept/CCD for her body.' cannon-es has a `collisionResponse` and a rudimentary `Body.ccdSpeedThreshold`/`ccdIterations` that is incomplete and widely known not to reliably prevent kinematic-vs-static tunneling through thin geometry. At chaseSpeed 3.0 m/s, per-frame displacement is only 0.05m (well under radius 0.30m) so steady-state tunneling is actually NOT the risk — the REAL risk is attackLungeSpeed 4.5 m/s combined with a dt spike: if a frame hitches to the clamped 0.05s max, displacement = 0.225m, still < radius, OK; but if dt clamp is forgotten or set higher, a 0.1s frame at lunge speed = 0.45m > radius 0.30m = tunnel through a 0.1m-thick door. The fix as written ('enable CCD') does not exist; the actual fix (manual sub-stepping: if intended displacement > radius*0.5, split the move into N kinematic sub-steps each followed by a contact check, OR raycast the swept segment and clamp) is the thing that must be specified and is not.
- AWARENESS DECAY MATH MEANS THE PLAYER WINS EVERY CHASE BY BREAKING LOS FOR ~5.6s. From CHASE the player only needs awareness to hit 0 to drop Granny to SEARCH. With awarenessDecayRate=18/s and a 0.5s grace, full 100 -> 0 takes 0.5 + 100/18 = 6.1s of no LOS. That sounds long, but combined with chaseSpeed 3.0 only barely exceeding player walk 2.6 and being SLOWER than sprint 4.6, a sprinting player trivially breaks LOS around one corner and is gone in <6s every single time. The chase is unwinnable for Granny against a competent player on 'normal' — the exact 'not fun / trivial' failure the risks section admits but the numbers guarantee. chaseSpeed MUST exceed sprint, or sprint must be stamina-gated, or both.
- NO MULTI-FLOOR / VERTICAL NAVIGATION. Granny's house is canonically multi-floor (that's the whole game — basement, ground, upstairs, stairs). The nav model is a single 2D grid ('2D array of cells'). Stairs, the defining traversal challenge, are completely unaddressed: a 2D grid cannot represent a staircase where cells overlap in XZ but differ in Y, and A* octile heuristic in 2D will path straight through the stairwell void. This is not a tuning issue; it's a missing dimension in the core data structure.

### Concrete Fixes
- FIX UPDATE ORDER: Split Granny's update into pre-step and post-step. PRE-step (before world.step): drain noise, run FSM transitions, plan/repath, compute desired velocity and SET body.velocity. POST-step (after world.step, so all transforms are current): run updateSight using the just-integrated player AND Granny transforms, integrate/decay awareness, store lastKnownPlayerPos. This removes the 1-frame perception lag entirely. Document it as: `grannyAI.prePhysics(dt); world.step(fixed, dt, 3); grannyAI.postPhysics(dt);`. Also fix the dt model: use a FIXED physics timestep (1/60 = 0.0167s) with cannon's built-in accumulator (world.step(1/60, dt, maxSubSteps=3)), and run AI logic once per render frame reading interpolated transforms — do NOT clamp a variable dt and feed it to both AI integration and physics; that desyncs perception integration from movement.
- REPLACE THE 'AABB moved' SIGNAL WITH AN EXPLICIT DIRTY SET. Don't poll all bodies. Have the gameplay code that moves furniture (player push impulse handler, Granny shove, door hinge constraint) push the affected body handle into a `movedThisStep` Set. After world.step, for each body in the set: call body.computeAABB(), diff vs body.userData.prevGridAABB, if changed rasterize old cells clear + new cells set, store new AABB, bump grid.version. Budget: cap at ~64 bodies/step; a 0.9x0.9x0.9m couch over a 0.5m grid touches ~9 cells, ~600 cell writes worst case = trivial. Only force a Granny re-plan if a changed cell index is on her currentPath (precompute a Set of path cell indices).
- SPECIFY THE GRID CONCRETELY AND ADD FLOORS. Define: grid origin = level AABB min (x,z), dimensions = ceil(extent/0.5). Make it an ARRAY OF 2D GRIDS, one per floor (floor index from body Y bucket), with explicit `portal` links for stairs (a stair = a sloped corridor of cells flagged isStair with a Y range and a cost multiplier 1.3, connecting floor[n] region to floor[n+1] region). A* operates on (floor, x, z) nodes; portal cells bridge floors. Octile heuristic uses XZ distance + abs(floorDelta)*stairCostEstimate. Without this, ship a single-floor house and say so loudly.
- REWRITE ANTI-TUNNELING AS MANUAL SUB-STEPPING (do not rely on cannon CCD). Each prePhysics: desired = velocity*fixedDt; if |desired| > body.radius*0.5 (0.15m), set N = ceil(|desired|/0.15) and either (a) raycast from current pos to current+desired against the static collision layer, and if it hits at fraction f, clamp velocity so she stops 0.05m short, or (b) do N internal kinematic micro-moves with contact checks. Apply the SAME to the lunge (4.5 m/s * 0.05 max-dt = 0.225m > 0.15 threshold, so the lunge ALWAYS sub-steps). Hard-assert dt clamp <= 0.0334 (2 frames) not 0.05.
- FIX THE CHASE SPEED / DECAY NUMBERS SO CHASES ARE WINNABLE FOR GRANNY YET ESCAPABLE. Set chaseSpeed normal = 4.2 m/s (just under sprint 4.6 so a fresh sprint opens a gap but stamina-limited sprint can't sustain it) AND gate player sprint with stamina (e.g. 4s sprint / 6s recharge) — coordinate this with the player/movement subsystem; without stamina, chaseSpeed must be >= 4.7. Keep awarenessDecay but add: in CHASE, lastKnownPlayerPos keeps Granny pathing aggressively to the corner the player vanished around for the full 6s, and on reaching it with still-no-LOS she enters SEARCH at that exact spot — so breaking LOS costs the player tempo even though it eventually works. Raise loop-kite shove/chord-cut to fire at 2.5s not 4s.
- RESOLVE catchRadius vs attack-resolve INCONSISTENCY. catchRadius=1.1m triggers ATTACK, attackLungeSpeed 4.5*0.35s=1.575m of travel, resolve if <=1.3m at lunge end. So she can trigger the lunge at 1.1m, travel 1.575m toward a player who runs away at 4.6 m/s (1.61m in 0.35s) — net she barely keeps pace and the 1.3m resolve is reachable only if player runs INTO her. State the intended math: lunge closes (4.5-4.6)*0.35 = -0.035m on a fleeing sprinter, i.e. she essentially cannot catch a sprinting player with the lunge — that's the design's escape window, fine, but make catchRadius the same as resolve (both 1.3m) or document why they differ, and make the lunge home slightly (turn toward player during lunge, capped at e.g. 180 deg/s) or it whiffs on any lateral juke.

### Missing Details
- How is Granny's FACING computed and updated? LOS cone needs a facing vector. Kinematic body has velocity but the design never says facing = normalize(velocity), nor how she faces while stationary/searching, nor a turn-rate cap (instant snap-to-face makes the cone feel like an aimbot — needs e.g. max yaw rate 180 deg/s).
- Player 'visibleFraction' sample points are undefined for the 3-ray case ('chest + 2 shoulder offsets') — offsets in world space or player-local? At what height? If the player crouches behind a 1.0m couch, do any sample points clear it? Crouch-hiding behind furniture is a core Granny mechanic and the sample-point geometry decides whether it works at all.
- Door state machine is referenced (open/closed/blocked/breakable-wood/locked-metal) but never defined as data, nor how door grid-cells sync with the hinge constraint angle. At what hinge angle does a door's cells flip walkable? A door ajar 20 deg is not passable by a 0.6m-diameter Granny.
- No spec for what happens when A* returns a PARTIAL path (the 4000-node cap bail) — does she walk the partial path and re-plan at the end, or stall? Undefined behavior here = Granny freezing mid-room.
- The reverse-LOS check for the reposition ('never in player's view cone') is asserted but the player's FOV/view frustum is never defined here, and a reverse-LOS that only checks the player's central ray will still let Granny pop into peripheral vision. Needs the player camera FOV (e.g. 75 deg) and multi-ray check, and should also fail if Granny would be within ~8m even off-camera (audio would betray a teleport).
- noiseQueue lifecycle: who clears it, what if multiple noises arrive in one frame (loudest wins? nearest? all processed?), and does a continuous sprint emit one event per footstep or per frame? 'sprint footstep = 1.0' implies discrete footstep events but the rate (steps/sec) is unspecified, which determines how often she re-targets.
- Animation/audio state is owned per-FSM-state, but transitions like Chase->Attack->Chase happen in <0.4s — no minimum-dwell or blend spec, so audio/anim will machine-gun on rapid transitions (the design's own 'audio lags state' fear, inverted into audio-thrash).
- No persistence/pause behavior: when the player is in a hiding spot (closet/under-bed, a Granny staple) is that a separate perception suppression, and does Granny's hearing still register breathing? Hiding is core to the loop and is entirely absent from this perception spec.
- Spawn/respawn after the player is caught-but-not-killed (Granny games typically jail/teleport the player) — does Granny reset to PATROL, keep awareness, get repositioned? Undefined, affects the whole multi-life loop.
- Memory/budget for the grid: a 20m x 20m x 3-floor house at 0.5m = 40x40x3 = 4800 cells, trivial; but if someone reads 'house' as 30x40m the per-floor A* open-set and the 4000-node cap interact — state the expected house dimensions so the cap and grid size are validated together.
